## 2. 5 个最重要的"教训"

### 教训 1: 测试全过 ≠ 正确 (W135 翻车)

我以为单测全过就稳了. W135 一次大 review 找出了 11 个 P0, 全部是 e2e 没覆盖的边界 case. 之后我加了一个铁律:

> **2-3 个独立 verifier 同时看, 谁先发现 P0 谁赢.**

W136-W148 累计 28+ 独立 verifier 抗审查, 找出了 25+ 真 P0. **测试全过只是入场券, 不是终点.**

### 教训 2: "用户没时间亲自测试" 意味着你必须自证

我没有精力请真实用户每天测试. 这意味着:

- 每个 PR 必须有 verifier 抗审查
- 每个 commit 必须有 commit message + diff 解释
- 每个版本必须写 release notes
- 抗审查找的 P0 必须修到 0

累计 22 周, 我写了 22 个 `REVIEW_*.md` + 22 个 `RELEASE_*.md` + 22 个 commit message. **自我证明 = 唯一可信源.**

### 教训 3: 0 真实用户 ≠ 0 价值 (W146 转向)

W142 时性能到顶 (perf 0.71 → 0.92), a11y 满分 1.00, LCP 6.9s → 1.7s. 我开始问: **然后呢?**

W146 我做了一件事: 接受 0 真实用户的事实, **不再加新功能, 而是让产品自己说话**:
- telemetry: 7 事件 + 1s 批量 + 30 天 retention (W146)
- 反馈按钮: 浮动右下角 + modal (W146)
- NPS: 7 天触发 + 0-10 滑块 (W146)
- Usage dashboard: 30 天折线 + Top 10 条形 (W146)
- 周报: 7 天数据 → Markdown/HTML, 可分享 (W147)
- 桌面 PWA 增强: 快捷键 + 桌面布局 (W148)

加起来 1.5 周. **战略上, 我建的不是产品, 是"反馈信号塔"**. 0 真实用户, 但有了听到用户的耳朵.

### 教训 4: 沙盒 sub-agent 不可靠, 主人兜底是常态

W132-W148 期间, 8 次 sub-agent 并行 (W136/W137/W140/W142/W144/W146/W147/W148), 7 次 fail. 模式:
- 启动慢
- Token Plan 上限触发
- 时间窗口内 0 完成

但 — **跟 W144 Agent B 0 deliverable 不同, W148 写了 13 文件**. 沙盒恢复越来越好. 主人兜底成 routine: 修测试 fail + 修 TS 编译 + 修 emoji 残留.

**5 周连击 (W144/W145/W146/W147/W148), 累计修 60+ 测试 fail + 10+ TS 修 + 1+ 真 P0 (W139).** 主人不是 sub-agent 的替代品, 是 sub-agent 失败后的最后一道防线.

### 教训 5: 文档是给自己看的

22 周下来, 我发现最值钱的不是代码, 是文档:
- `CHANGELOG.md` (4.8KB) — 138 个 release 的来龙去脉
- `REVIEW_*.md` (22 份) — 每次 review 的 P0 列表
- `RELEASE_*.md` (22 份) — 每次发版的 release notes
- `ARCHITECTURE.md` — 整体架构
- `DEV_LOG.md` — 决策日志

**没有文档, 22 周后没人能懂这个项目 (包括我自己)**. W150 的目标: 写博客 + 写技术架构图 + 写 "如何贡献".

## 3. 22 周踩过的 10 个最大坑

1. **W139 LessonDetailPage rules-of-hooks** — React useMemo 放在 early return 之后, 业务上偶尔崩, 但只在某些 prop 顺序下崩. 找了 3 周才发现.
2. **W136 删 syncManager.ts** — 整文件 372 行没人调用, 删了之后 P0-1/3/4 一次消解.
3. **W145 词库 6.3MB 全量加载** — LCP 6.9s, 拆 25 chunks 后 1.7s. 0 业务变化.
4. **W140 7 单测期望过期** — 测试 v2.1.12 → v2.1.19/20 同步.
5. **W128 跨 tab 同步** — 没用 BroadcastChannel, 用 IDB + 自定义事件, 复杂度高.
6. **W125 暗色模式** — 全 CSS 变量重写, 30+ 组件逐个调.
7. **W123a-d AIChat 改造** — 4 个版本迭代, 才找到 v2 的体验.
8. **W122 PDF 上传** — pdfjs-dist 6MB, 拆 vendor 单独 chunk.
9. **W104 数据导出** — 全量 JSON 6.3MB, 用户根本不会导出, 后来给 dataExport 拆独立 chunk.
10. **W98 暗色 toggle 闪烁** — 没在 main.tsx 加 `classList.add('dark')`, 用户首屏会闪一下白.

## 4. 我没做对的 5 件事

1. **没早点招真实用户** — 0 真实用户让我陷入"自证"循环, 22 周后才真正面对这个问题.
2. **W82 之前没抗审查** — 早期 14 周的代码, 大半没经过 verifier, 后面 W135 才暴露一堆 P0.
3. **W143 之前没测过 Lighthouse** — 性能到顶是后知后觉, 之前以为"功能能用就行".
4. **W146 之前没做 telemetry** — 0 用户行为数据, 等于盲人摸象.
5. **W150 之前没写博客** — 做了 22 周才想起总结, 早就该边做边写.

## 5. v3 战略 (2026-08-11, W145 时)

W142-W145 性能到顶, 我意识到 0 真实用户的核心问题不是技术, 而是 —

> **技术到顶 ≠ 产品好, 产品好 ≠ 有人用.**

所以我做了 v3 战略 (跟 user 的 3 份 plan review 后), 转向:

- ❌ **拒绝**: A 多语言主体 (时机未到) / B 主动营销 (没产品就别营销) / C 微信小程序+Android (0 ROI) / D 再改 UI (已经改 4 轮)
- ✅ **接受**: E 反馈回路 (W146 反馈 / W147 周报 / W148 桌面) → W149 真实用户招募

**核心心法**: 不要列功能, 让产品自己说话. 听到真实用户声音, 再决定 W150+ 干什么.

## 6. 给"独立产品"同行的 5 个建议

1. **不要列 100 个功能, 列 5 个会出问题的** — 我列了 8 大功能, 22 周做完, 0 用户. 当时应该砍到 2-3 个, 5 周做完, 然后看用户用不用.
2. **测试全过 ≠ 正确** — 抗审查不是"找 bug", 是"找自己看不见的盲点". 多个独立 agent 同时看.
3. **telemetry + 反馈回路 = 产品的耳朵** — 没耳朵, 你只能自己脑补用户.
4. **文档 = 你未来的自己** — 22 周后没文档, 项目就是个迷宫.
5. **0 真实用户不是借口** — 拉 5-10 个朋友 1 周内测, 比你闭门造车 22 周有效 100 倍.
